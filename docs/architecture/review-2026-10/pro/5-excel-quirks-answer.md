# Excel quirks and newer behaviours: an executable-probe catalogue for DNA Calc

**Prepared 31 October 2026. Coverage: 381 probe specifications across 12 areas.**

This catalogue supplies a third source of compatibility tests alongside individual-function recordings and real-workbook recalculation. Each row specifies a small experiment, a candidate expectation or **measure**, the implementation trap, and a source. The formulas and fixtures are original test designs informed by the linked Microsoft documentation and announcements.

**These are probe specifications, not recorded Excel results. I have not executed them in Excel or DNA Calc.** Even an H-confidence expectation must be recorded on a designated Excel profile before it becomes a golden answer. Approximate numbers describe mathematical magnitude; they never specify the binary64 oracle. Where a source is incomplete, ambiguous, apparently inconsistent, or describes unsupported input, the table deliberately asks for measurement.

## How to execute the tables

### Common fixture conventions

1. **Use a new workbook for each row**, except for explicitly described multi-workbook scenarios. Use a new Excel process for application-state and first-opened-workbook tests. Create `Sheet1` unless the row specifies other sheets. All unmentioned cells are genuinely empty; there are no tables, merged cells, filters, names, links, hidden rows, or custom formatting unless the row adds them.
2. **Baseline settings:** en-US formula-entry language and regional parsing, 1900 date system, Automatic calculation, iteration off, precision as displayed off, General cell format, and sufficiently wide columns. Baseline dynamic-array tests use a recorded Compatibility Version 2 profile where available; use a separate Version 1 profile for legacy comparisons. Rows explicitly override these defaults. Do not silently upgrade a workbook opened for a compatibility test.
3. **Formula entry:** use invariant A1-style `Formula2` for ordinary modern formulas. Commas separate arguments and array columns; semicolons separate array rows. A row explicitly requesting `Formula`, `FormulaLocal`, `Formula2Local`, R1C1, CSE, typed UI entry, or a file patch must use that entry route. Retain the entered string and Excel's resulting formula properties. Microsoft documents Formula and Formula2 as different evaluation dialects. [Formula versus Formula2][Y-S04]
4. **Cell types are literal requirements.** “Text `001`” means a stored text cell whose payload is exactly those three characters. It does not mean numeric 1 with a custom display format. “Truly empty” means `ClearContents` with no formula. A cell containing `=""` contains a formula returning zero-length text. Leading apostrophes used to force UI text entry are not part of the text payload. Use a known text-preserving writer and verify the stored type.
5. **Range setup is positional.** `A1:A3: 10;20;30` places those three numbers down the column. A matrix such as `{1,2;3,4}` describes rows `[1,2]` and `[3,4]`. Output array notation records both dimensions and element types; `""` denotes empty text, and `#N/A` without quotes denotes an error value. Table headings and sheet names shown in backticks are exact text.
6. **Execute operations in the stated order.** Establish initial values and perform any requested initial calculation before applying edits. Snapshot at each stated checkpoint. For spill/array probes, enter the designated formula only in its anchor and leave the output region clear. If a candidate formula unexpectedly spills farther than anticipated, capture it before installing another output formula that could obscure it.
7. **Separate calculation from observation.** For completed-result cases, use the stated recalculation action and wait for the relevant calculation to finish. For stale-cache, cancellation, link, and iteration cases, capture the specified intermediate state first. A preliminary full rebuild would destroy the condition those tests are designed to observe.
8. **All destructive operations act on generated fixtures.** The delete, overwrite, precision-as-displayed, Break Links, CSV, and package-editing cases are executable test scenarios, not instructions to alter a real user's workbook. Restore application-wide options or discard the isolated Excel process after each scenario.

Where an operation requires the UI, a workbook object, or a package editor, the probe is a short scenario rather than a single expression. This is necessary to test editing, import, calculation scheduling, and serialization behaviour. The catalogue is ready to translate into runner cases; it is not a supplied automation executable.

### Expectations, confidence and version marks

| Mark | Meaning and treatment |
| --- | --- |
| **H** | The central rule has strong documentation support and the fixture has a straightforward expected outcome. This is confidence in the candidate specification, not evidence of a completed Excel run. |
| **M** | A plausible expectation follows from documented behaviour or a boundary inference; record it before asserting it. |
| **E** | Exploratory: exact output, ordering, error, timing, availability, or representation needs an Excel observation. |
| **measure** | Do not fill in a guessed scalar. Record the requested values, types, shapes, error codes, formula text, state, or trace. A nearby “expected” or mathematical value is a hypothesis to investigate. |
| **[V]** | Version-sensitive or introduced after older Excel releases. Feature-test the target build; do not read this mark as a precise minimum-version promise unless the row states one. |
| **[V, preview]** | Opt-in, evolving behaviour in a separately identified preview profile. Do not merge it into the ordinary Microsoft 365 corpus. |

Some confidence cells qualify different subcases separately. An H candidate does not convert a neighbouring **measure** subcase into a fixed assertion. Sources support the relevant documented rule or motivate the boundary experiment; a generic function page is not a claim that Microsoft published the exact test fixture or its observed result.

## Version boundaries that affect this catalogue

**Workbook compatibility is now an explicit input.** Microsoft's support table says new Current Channel workbooks use Version 2 from April 2026, while older workbooks are treated as Version 1; recommendations still vary by channel. The Unicode probes T004–T008 therefore compare workbook profiles as well as application builds. [Compatibility Versions][T-S05]

**Nested arrays need a separate preview corpus.** Microsoft's September 2026 Excel announcement describes lists, arrays stored inside cells, nested arrays, and the new FLATTEN/HAS functions in Insiders Beta. Y051–Y052 test that capability explicitly, and Y038/Y040/Y042 compare relevant old and new boundaries. [September arrays announcement][I-S01]

The detailed preview announcement specifies Compatibility Version 3, while the general compatibility support table still lists Version 2 as Beta's highest version at the time of this research. Preserve that documentation discrepancy. Record which settings and features the actual installation exposes; unsupported, not-enabled, and semantically failing are different outcomes. [Nested-array preview][Y-S35]; [Compatibility Versions][T-S05]

**AccuracyVersion is a different switch.** Microsoft also exposes `Workbook.AccuracyVersion`, selecting algorithms for some older statistical and financial functions. Record it separately from Compatibility Version and `CalculationVersion`; S007–S008 exercise it directly. [AccuracyVersion][S-S07]

## Suggested first recording pass

The order below is an implementation recommendation derived from the probes, not a claim about where DNA Calc currently has defects.

| Priority | Record first | What the evidence resolves |
| --- | --- | --- |
| 1. Value types and coercion | A020–A025; G001–G005, G017–G020; E002, E019–E023; L024, L026, L029 | Which distinctions survive parsing, evaluation, aggregation, and collection. |
| 2. References and shapes | R014, R026–R038; Y001–Y013, Y015–Y030; G011–G012, G028; E025 | Where reference identity, row/column shape, and spill placement affect semantics. |
| 3. Numeric compatibility | A001–A019, A031–A032; S006–S010, S014, S018, S022–S023; F002, F005–F019 | Input conversion, accumulation, algorithm selection, solver roots, and exact-bit boundaries. |
| 4. Version and locale | T002–T012, T033–T040; Y044–Y052; S007–S008; L001–L015, L027–L028 | Which results belong to distinct feature, workbook, locale, or file-format profiles. |
| 5. Stateful execution | N008–N032; C001–C028; L022–L023, L030 | Whether the mutation/recalculation pipeline reproduces observable state transitions. |

Start each family with its simple control, then record the surprising boundary. Once a row is confirmed, preserve the fixture and observations before adding generated variants. An unexpected result should first become a reproducible experiment, then a compatibility decision.

## Appendix A — Minimal scheduling diagnostic

The following VBA helper supports C005–C008, C012 and C025. Put it in a standard module of a disposable `.xlsm` fixture. It returns its argument unchanged and appends a label to an in-memory trace. `ResetProbeTrace` and `ReadProbeTrace` are invoked by the host or Immediate window, not from cells. The `Application.Volatile` call follows the documented UDF mechanism. [Application.Volatile][C-S07]

```vb
Option Explicit

Public ProbeTrace As Collection

Public Sub ResetProbeTrace()
    Set ProbeTrace = New Collection
End Sub

Public Function ProbeEcho(ByVal label As String, _
                          ByVal x As Variant, _
                          Optional ByVal isVolatile As Boolean = False) As Variant
    Application.Volatile isVolatile
    If ProbeTrace Is Nothing Then Set ProbeTrace = New Collection
    ProbeTrace.Add label
    ProbeEcho = x
End Function

Public Function ReadProbeTrace() As String
    Dim i As Long
    Dim result As String
    If ProbeTrace Is Nothing Then
        ReadProbeTrace = ""
        Exit Function
    End If
    For i = 1 To ProbeTrace.Count
        If i > 1 Then result = result & ","
        result = result & CStr(ProbeTrace(i))
    Next i
    ReadProbeTrace = result
End Function
```

For a typical case: construct the row's fixture, calculate to establish a clean baseline, run `ResetProbeTrace`, perform only the specified trigger, and collect the trace and cell values. Trace calls are observations, not assertions of an exact universal call count. Run an uninstrumented counterpart when the helper could affect the property under investigation. VBA UDF instrumentation is unsuitable for inferring the native multithreaded scheduler's exact ordering; C022 therefore uses ordinary worksheet formulas and captures results directly. [Calculation performance][C-S05]

## Appendix B — Oracle record and comparison contract

### Record the environment once per run

Use a stable profile key and retain the actual manifest behind it:

| Profile field | Required contents |
| --- | --- |
| Excel identity | Product/version, full build, update channel, Windows/Mac/Web, process architecture, and feature-flag outcomes. Record an unavailable feature explicitly. |
| Host execution | OS version, CPU model/architecture and available instruction features where obtainable, thread settings/count, and whether native or emulated execution is used. On hosted Web Excel, mark inaccessible backend CPU details unknown. |
| Workbook semantics | Compatibility Version, AccuracyVersion where exposed, date system, precision-as-displayed flag, calculation mode, iteration flag/limits, and workbook/application CalculationVersion. |
| Locale and time | UI language, regional locale, actual decimal/group/list separators, calendar/date parsing settings, two-digit-year cutoff for entry tests, code page where relevant, host time zone and timestamp. |
| Entry and transport | UI versus API versus file import; Formula/Formula2/local/R1C1/CSE; `.xlsx`/`.xlsb`/`.xlsm`/CSV; import options; link-update policy; calculation-before-save flag. |
| External state | Source-workbook hashes and open/closed state, service availability for T040, clock/random controls or their absence, and explicitly permitted add-ins/helpers. |

These fields are a proposed runner manifest. Record unavailable properties as unavailable, rather than synthesizing values from the marketing version name. Capture application-wide options before each stateful scenario and verify the intended values after installing them.

### Preserve input and output types

For every cell output, retain its address, value kind, and exact payload. Numeric outputs should include the double's **64-bit hexadecimal representation** and a round-trip decimal string. On Windows COM, `Value2` avoids the Currency/Date Variant coercions used by `Value`; record the raw returned type before converting it. [Value2][L-S23]

Strings should retain their exact UTF-16 code-unit sequence as well as a readable rendering. This matters for the deliberate partial-surrogate tests; a UTF-8 encoder that substitutes replacement characters would lose the observation. Errors should retain the native error payload/code and readable spelling. Do not use error text alone as the type discriminator. For a file cache, also retain the relevant serialized cell type and payload; SpreadsheetML explicitly separates formula text from its cached result. [Cell values][L-S17]; [SpreadsheetML formulas][L-S18]

For array and reference probes, record dimensions, element types, output coordinates, anchor ownership, formula text, and placement error separately. An expression can produce an array successfully while the attempted spill fails; E025 is designed to expose that boundary. For a reference result, also use the row's specified `ISREF`, `ROWS`, `COLUMNS`, colon/intersection, or consumer formulas to observe properties that a scalar read would erase. [Spilled arrays][Y-S01]; [INDEX][R-S06]

Retain displayed text and number-format code as separate observations for display cases. They are useful evidence, but are not substitutes for raw values. Store the original fixture and the post-operation workbook, plus hashes, when the scenario depends on mutations or saved caches. Keep pre-calculation and post-calculation snapshots separate.

### A result is more than pass/fail

Recommended outcomes are `supported_match`, `supported_mismatch`, `unmeasured`, `unsupported_feature`, `entry_rejected`, `environment_blocked`, `nondeterministic_observation`, and `not_exercised`. These are runner categories, not Excel worksheet values. For example, a missed cancellation in C023 is `not_exercised`, and unavailable preview syntax is not automatically a semantic regression in the stable profile.

Use several comparison layers:

1. **Entry and structure:** accepted/rejected formula, normalized formula text, reference binding, cell type, array shape, and operation effects.
2. **Semantic result:** matching typed values and error classes, with the documented/profile-specific treatment of missing and empty values.
3. **Exact numerical result:** identical binary64 bits when this is the selected profile's contract. Keep ULP distance as a diagnostic for mismatches, not as an automatic relaxation of the goal.
4. **State and scheduling:** the specified stale/fresh value checkpoints and traces, under the same sequence of actions.
5. **Rendering and transport:** format-sensitive display, serialized cache, and round-trip differences when the row explicitly targets them.

These comparison layers are a proposed engineering approach. They help classify a mismatch without discarding the original observation. In particular, an approximate expectation in this document is never sufficient to create a bitwise golden value.

### Handling measured surprises

For an unexpected result, rerun the same fixture in a fresh process with the same settings, preserve the observation, and reduce the case before modifying either engine expectations or implementation. Then vary one dimension at a time: input entry route, reference versus literal, scalar versus array, compatibility setting, locale, or build. Maintain separate oracle records whenever a difference is repeatable and attributable to a profile.

Treat unsupported search preconditions, undocumented error ordering, solver convergence, and preview behavior as observations with a defined scope. R002/R008/R018 intentionally ask what Excel actually does with unsorted inputs; they do not infer a universal algorithm from one example. Random and service-backed cases should use state/range/type/availability assertions and recorded samples, rather than requiring unrelated executions to produce identical values.
