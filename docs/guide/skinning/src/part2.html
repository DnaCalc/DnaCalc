Two host levels, enforced by crate boundaries

Level 0: formulas without a workbook

calc-formula-host evaluates one formula with test inputs, traces its parts and applies a conditional-format rule to the result. Its dependency closure may not contain calc-engine or calc-host. The standalone Formula Explorer runs here and ships no workbook engine.

Level 1: the workbook

calc-host owns cells, the calculation graph, recalculation, the view part and the history. calc-skin-host serves it: SkinHost::connect(origin, policy) returns a Connection whose origin and write policy are fixed for its life.

pub fn commit_edit(&mut self) -> Changes {
    let Some(edit) = self.edit.clone() else { return Changes::default(); };
    if !matches!(self.seam(), Seam::Idle | Seam::Queued) { return Changes::default(); }
    let batch = Batch {
        id: String::new(),
        workbook: Some(edit.workbook),
        base: Some(edit.base),                 // the model revision the draft was started on
        expects: vec![cell_source(edit.at)],   // refuse if someone else changed this cell since
        selection_seq: None,
        label: None,
        changes: vec![Change::Model(ModelChange::Enter { at: edit.at, text: edit.text })],
    };
    self.start(batch, Submission::Draft)       // preview first, then commit when clean
}

The skin interface

What a view author writes against. It is small on purpose: a trait, a handle, typed questions, and one way to change anything.

View

A view is a crate with an install function. This is the whole of Classic's view file. The grid, its commands and its watches live in dna-grid; the view composes them.

struct Classic;

impl View for Classic {
    fn spec(&self) -> ViewSpec {
        ViewSpec { id: ViewId(ID.into()), title: "Classic", profile: "excel-365-win-en-us" }
    }

    fn commands(&self, session: Session) -> Vec<ViewCommand> {
        let view = self.spec().id;
        session.set_key_tips(view.clone(), excel_key_tips::EXCEL_KEY_TIPS);
        let mut commands = dna_grid::commands(&view, session);
        commands.extend(clipboard::commands(&view, session));
        commands.push(
            ViewCommand::new(&view, "classic.key-tips", "Key tips", &["F10"], move |_| {
                session.toggle_key_tips();
                Ok(())
            })
            .when("!editing"),
        );
        commands
    }

    fn mount(&self, session: Session) -> MountedView {
        MountedView::exact(dna_grid::mount(session))
    }
}

pub fn install(registry: &mut Registry) { registry.view(Classic); }

Typed queries

A view names a query type and receives that type's answer. JSON bodies and field-name reads are not allowed on either side: the host encodes each answer with the same type's Query::encode, and a body of the wrong shape decodes to Refusal::Transport, never to a default.

pub trait Query: Clone + PartialEq + 'static {
    type Answer: Clone + PartialEq + Serialize + DeserializeOwned + 'static;
    fn request(&self) -> WorkbookQuery;                       // the wire form
    fn encode(answer: &Self::Answer) -> Result<Value, Refusal>; // the host calls this and nothing else
    fn decode(answer: Answer<Value>) -> Result<Answer<Self::Answer>, Refusal>;
}

Frames and watches

A watched query records what it read. When a commit or a calculation touches that footprint, the host answers it again and puts every update and event of that step into one Frame { stamp, events, updates }. The client applies a frame whole before any signal fires. Cells travel differently: a watched Cells query arrives as binary tiles, with its completion barrier in the same frame as the other updates.

While a macro runs with ScreenUpdating = False, next_frame returns nothing, which is exactly what Excel shows.

Preview and the seam

Every change from every view goes through one place. The seam is a state of the client, not a convention each view remembers.

The host computes the preview from the edits it prepared. Preview::kind() returns Model, Presentation or Both from the writes themselves, never from what the caller claimed. The Bridge shows the result as an inline label, Model change · B4, visible in the screenshot in section 5.

The one history

Ctrl+Z first undoes inside an open text draft. Once committed, it undoes the top entry of the workbook's history, whichever view made it. A layout edit and a cell edit sit in the same list, each labelled with its ChangeKind and its Origin.

pub struct HistoryEntry {
    pub id: EntryId,
    pub at: Stamp,
    pub label: String,              // "Entered B4", "Edited layout"
    pub origin: Origin,             // User { view } | Agent | Macro | Automation | Extension
    pub kind: ChangeKind,           // Model | Presentation | Both
    pub targets: Vec<Target>,
    pub cells_touched: u64,
    pub reversibility: Reversibility,
    pub group: Option<String>,
    pub unreviewed: bool,           // set for a WritePolicy::ApplyThenReview connection
}

Commands and keymaps

Everything a person, a skin, a macro's view request or an agent can ask the page to do is a command with an identity, registered once in a CommandTable with the condition under which it can run. A key chord, a Deck button, the command search and a skin's named sequence all end in CommandTable::run. A view has no key handler.

Capabilities and typed refusals

A host says up front what it can do (Capabilities { read_only, supported, platform_reserved_chords }), and every failure is a typed Refusal. A view contains no platform branches: a missing capability arrives as data.

RefusalMeaning
NotModelled { owner, what }Not implemented yet. Names the work package that owns it and counts as a failure in every statistic.
NotAvailableHere { capability, route }This host cannot do it (a native add-in in a browser), with a route to one that can.
Conflict { base, conflicts }Something in the batch's expects changed since base. Nothing is overwritten silently.
StaleSelection · ReadOnly · Protected(SourceRef) · Validation { target, reason } · Excel { reason }Excel's own reasons an edit cannot land, kept apart from ours.
OverBudget { counts, alternatives }The question was too large for its budget. Offers narrower scopes instead of hanging.
PolicyRefusedThe connection's WritePolicy does not allow it: a Look or Propose connection cannot commit.
RequiresWorkbook · Invalid · Irreversible · SchemaMismatch · TransportA level-0 formula that needs a workbook, a malformed request, an operation that cannot be undone, and the two wire failures.

Classic Preview

dnacalc.com/app/preview/, with a six-row loan model typed in and F2 pressed on B4.

  2. View switcher and Go to. One button per registered view, each a view.<id> command; Alt+Q runs shell.search over commands and cells.
  3. Deck. Each button names a command; its data-command attribute is the command identity (edit.undo, edit.redo, calc.calculate, shell.details).

  5. Bridge · formula bar. Bound to the session's one EditSession; the entry text comes from the Formula { at } watch on the active cell.
  6. The seam, inline. Model change · B4: the destination and the kind of the change in progress, before it is committed.
  7. Stage · the sheet (dna-grid). Watches Cells for the 36 by 18 page holding the active cell, and Geometry for its sheet. Arrows, F2, Delete are grid.* commands.
  8. Sheet Tabs. Sheet descriptors from Summary.
  9. Strip. Input mode (Edit), the calculation word from CalcState, where the selection is in this view, held notebook drafts, and the latest notice. It is not hidden under any skin.
