The Skinning Guide

A DNA Calc workbook is an Excel workbook. What you see around it is replaceable: views are compiled engines, skins are data, pages are component trees, and one contract sits underneath them all. This guide shows how that is built, how it reaches the calculation engine, and how to make a skin of your own.

01

The idea in one picture

There is one workbook, one selection and one undo history. Everything on screen is a way of looking at them.

A view is a compiled engine

A Rust crate that implements View. It is given a Session and nothing else: no shell type, no carrier, no other view. Classic, Inspector, Notebook and App exist; Model map is designed.

A skin is data

A dna.skin/1 JSON manifest. It restyles and rearranges the views that exist. It cannot add behaviour, because it holds no code.

A page is a component tree

A dna.page/1 flow layout of standard components, each bound to workbook cells. One grammar, one renderer.

One contract underneath

calc-skin is the only thing page code and host code share. It reaches no engine, no file codec and no UI toolkit.

02

Philosophy

Four rules shape every type in the contract. A skin author meets all four within the first hour.

No more than Excel

The engine calculates what Excel calculates and nothing else. A view may show a workbook in a new way; it may not give it a new meaning. Every change to the model is an operation Excel itself can express. A notebook cell is a worksheet cell. A map box is a named cell on a visible sheet.

Honesty about state

No value crosses the contract without saying where it came from. Shown<T> carries a Provenance; every answer carries a Coverage; every query takes a Budget. A component cannot draw a stale number as a fresh one, because the type does not let it lose the difference.

Model edits and presentation edits are different things

Moving a panel is not editing a spreadsheet. The contract keeps two revisions, Stamp.model and Stamp.view. A presentation change never advances the model revision, and the preview tells you which kind you are about to make before you make it.

No code in files

A workbook carries declarations: anchors, view documents, notes. Skins and pages are JSON with no scripts, no expressions, no HTML and no URLs. Opening a file runs nothing and fetches nothing.

Honesty, as types

These are the actual definitions in crates/calc-skin/src/workbook.rs. Seven provenances, two coverages, three kinds of evidence.

pub struct Shown<T> { pub value: T, pub provenance: Provenance }

pub enum Provenance {
    Empty,
    Literal,
    Calculated { calc: CalcGeneration },
    AsSaved,                                   // from the file; this engine has not calculated it
    External { source: String, observed_at: Option<u64> },
    Stale    { since: Revision, cause: StaleCause },
    Refused  { owner: String, reason: String }, // typed not-modelled refusal naming its owner
}

pub enum Coverage { Complete, Partial { done: u64, total: Option<u64>, why: PartialWhy } }
pub struct Answer<T> { pub stamp: Stamp, pub coverage: Coverage, pub body: T }

pub enum Evidence<T> {                        // what ran is never confused with what is inferred
    Observed    { observer: String, at: Stamp, body: T },
    Derived     { from: Derivation, at: Stamp, body: T },
    Unavailable { reason: String },
}

Two host levels, enforced by crate boundaries

Level 0: formulas without a workbook

calc-formula-host evaluates one formula with test inputs, traces its parts and applies a conditional-format rule to the result. Its dependency closure may not contain calc-engine or calc-host. The standalone Formula Explorer runs here and ships no workbook engine.

Level 1: the workbook

calc-host owns cells, the calculation graph, recalculation, the view part and the history. calc-skin-host serves it: SkinHost::connect(origin, policy) returns a Connection whose origin and write policy are fixed for its life.

The first lines of that journey, as written in the runtime:

pub fn commit_edit(&mut self) -> Changes {
    let Some(edit) = self.edit.clone() else { return Changes::default(); };
    if !matches!(self.seam(), Seam::Idle | Seam::Queued) { return Changes::default(); }
    let batch = Batch {
        id: String::new(),
        workbook: Some(edit.workbook),
        base: Some(edit.base),                 // the model revision the draft was started on
        expects: vec![cell_source(edit.at)],   // refuse if someone else changed this cell since
        selection_seq: None,
        label: None,
        changes: vec![Change::Model(ModelChange::Enter { at: edit.at, text: edit.text })],
    };
    self.start(batch, Submission::Draft)       // preview first, then commit when clean
}

The skin interface

What a view author writes against. It is small on purpose: a trait, a handle, typed questions, and one way to change anything.

View

A view is a crate with an install function. This is the whole of Classic's view file. The grid, its commands and its watches live in dna-grid; the view composes them.

struct Classic;

impl View for Classic {
    fn spec(&self) -> ViewSpec {
        ViewSpec { id: ViewId(ID.into()), title: "Classic", profile: "excel-365-win-en-us" }
    }

    fn commands(&self, session: Session) -> Vec<ViewCommand> {
        let view = self.spec().id;
        session.set_key_tips(view.clone(), excel_key_tips::EXCEL_KEY_TIPS);
        let mut commands = dna_grid::commands(&view, session);
        commands.extend(clipboard::commands(&view, session));
        commands.push(
            ViewCommand::new(&view, "classic.key-tips", "Key tips", &["F10"], move |_| {
                session.toggle_key_tips();
                Ok(())
            })
            .when("!editing"),
        );
        commands
    }

    fn mount(&self, session: Session) -> MountedView {
        MountedView::exact(dna_grid::mount(session))
    }
}

pub fn install(registry: &mut Registry) { registry.view(Classic); }

Typed queries

A view names a query type and receives that type's answer. JSON bodies and field-name reads are not allowed on either side: the host encodes each answer with the same type's Query::encode, and a body of the wrong shape decodes to Refusal::Transport, never to a default.

pub trait Query: Clone + PartialEq + 'static {
    type Answer: Clone + PartialEq + Serialize + DeserializeOwned + 'static;
    fn request(&self) -> WorkbookQuery;                       // the wire form
    fn encode(answer: &Self::Answer) -> Result<Value, Refusal>; // the host calls this and nothing else
    fn decode(answer: Answer<Value>) -> Result<Answer<Self::Answer>, Refusal>;
}

// a component asking for one page of rows, as dna-kit's page renderer does
let rows = session.following::<query::Rows>();
match rows.at(Some(query::Rows { source, filter: vec![], sort: vec![], window: RowWindow { offset: 0, limit: 12 } })) {
    Live::Ready(answer) => /* answer.body: RowPage, answer.coverage, answer.stamp */,
    Live::Refused(reason) => /* say why */,
    _ => /* Idle, Loading or Outdated */,
}

Frames and watches

A watched query records what it read. When a commit or a calculation touches that footprint, the host answers it again and puts every update and event of that step into one Frame { stamp, events, updates }. The client applies a frame whole before any signal fires. Cells travel differently: a watched Cells query arrives as binary tiles, with its completion barrier in the same frame as the other updates.

While a macro runs with ScreenUpdating = False, next_frame returns nothing, which is exactly what Excel shows.

Preview and the seam

Every change from every view goes through one place. The seam is a state of the client, not a convention each view remembers.

The host computes the preview from the edits it prepared. Preview::kind() returns Model, Presentation or Both from the writes themselves, never from what the caller claimed. The Bridge shows the result as an inline label, Model change · B4, visible in the screenshot in section 5.

  • PreviewDepth::WritesOnly
  • PreviewDepth::WithEffects → NotModelled { owner: "dc-zh096" }

The one history

Ctrl+Z first undoes inside an open text draft. Once committed, it undoes the top entry of the workbook's history, whichever view made it. A layout edit and a cell edit sit in the same list, each labelled with its ChangeKind and its Origin.

pub struct HistoryEntry {
    pub id: EntryId,
    pub at: Stamp,
    pub label: String,              // "Entered B4", "Edited layout"
    pub origin: Origin,             // User { view } | Agent | Macro | Automation | Extension
    pub kind: ChangeKind,           // Model | Presentation | Both
    pub targets: Vec<Target>,
    pub cells_touched: u64,
    pub reversibility: Reversibility,
    pub group: Option<String>,
    pub unreviewed: bool,           // set for a WritePolicy::ApplyThenReview connection
}

Commands and keymaps

Everything a person, a skin, a macro's view request or an agent can ask the page to do is a command with an identity, registered once in a CommandTable with the condition under which it can run. A key chord, a Deck button, the command search and a skin's named sequence all end in CommandTable::run. A view has no key handler.

Capabilities and typed refusals

A host says up front what it can do (Capabilities { read_only, supported, platform_reserved_chords }), and every failure is a typed Refusal. A view contains no platform branches: a missing capability arrives as data.

RefusalMeaning
NotModelled { owner, what }Not implemented yet. Names the work package that owns it and counts as a failure in every statistic.
NotAvailableHere { capability, route }This host cannot do it (a native add-in in a browser), with a route to one that can.
Conflict { base, conflicts }Something in the batch's expects changed since base. Nothing is overwritten silently.
StaleSelection · ReadOnly · Protected(SourceRef) · Validation { target, reason } · Excel { reason }Excel's own reasons an edit cannot land, kept apart from ours.
OverBudget { counts, alternatives }The question was too large for its budget. Offers narrower scopes instead of hanging.
PolicyRefusedThe connection's WritePolicy does not allow it: a Look or Propose connection cannot commit.
RequiresWorkbook · Invalid · Irreversible · SchemaMismatch · TransportA level-0 formula that needs a workbook, a malformed request, an operation that cannot be undone, and the two wire failures.

What a skin is

A skin is one JSON document. It can be read in a minute, checked in under a second, and it cannot do anything a person could not do by hand in the application.

A complete skin, annotated

This file is in the repository at docs/guide/skinning/examples/calm-review.dnaskin.json. Its palette is the one the CLI's own test accepts.

  1. Schema and base. extends must be dna:default or dna:explorer. level says which host level the skin is for.
  2. Theme. A base theme (cockpit-light, cockpit-dark, high-contrast), a density (working, reading), and overrides of the open tokens. Formula text size may be 10 to 32 px.
  3. Shell. Deck compactness, panels docked right or bottom (an instrument id or one of this skin's page ids), and extra Strip read-outs pinned to an address.
  4. Keymap. Bindings over the Excel profile. when uses the condition grammar of section 4. The whole layer is refused if any binding is wrong.
  5. Command sequences. An id starting skin., a label, and steps that name built-in commands. A sequence runs only when a person invokes it, and stops at the first step that refuses.
  6. Per-view settings. A free JSON object per view id, read by that view.
  7. Pages. dna.page/1 trees by id. Here one page, docked on the right by item 3.

Strand tokens and the contrast check

Strand is DNA Calc's design language: petrol chrome around bright paper, and colour only where it means something. A skin may move the neutral surfaces. It may not touch the signals.

Open to a skin

  • bg paper paper-2surfaces; surface.panel is an alias for paper-2
  • ink ink-2 ink-3text; ink.secondary is an alias for ink-2
  • line line-softborders and grid rules
  • chrome chrome-2 chrome-ink chrome-ink-2the Mast, Bridge and Strip
  • accent accent-ink accent-softstructure and interactive accents
  • formula.font.size10 to 32 px

Closed to every skin

  • Rederrors, and nothing else
  • Amberfocus and "now": the cursor, the selection, a running calculation
  • Signal orangeexternal and volatile values
  • Greena fresh, calculated value
  • Any other token namethe validator answers "The token … cannot be changed by a skin"
  • The workbook's own cell formattingan authored fill or a red negative is model content, not theme

dna_strand::resolve(theme, overrides) applies the overrides and then checks every sanctioned foreground and background pair of that theme. There are 61 pairs in SANCTIONED_PAIRS: 22 for cockpit-light, 17 for cockpit-dark, 22 for high-contrast. Text needs 4.5:1 (7:1 under high contrast). One failing pair refuses the whole skin, with the pair and the ratio in the message.

Keymaps and Excel key tips

A skin's bindings form one layer of the keymap, below the safety, editor and component layers and above the view's own profile. The validator refuses a skin that binds any of these chords:

  • Esc
  • Ctrl+Z
  • Ctrl+Y
  • F4
  • Ctrl+Enter
  • Alt+Q
  • Ctrl+Alt+1
  • Alt+Shift+1

It also refuses two bindings for the same chord whose conditions can both hold, an unknown condition, and (when the skin is applied to a running page) a command that is not registered. Classic's key tips are data: a table of Excel's own letter sequences in dna-view-classic/src/excel_key_tips.rs, shown with F10. A tip whose command is not built answers with a typed not-modelled notice naming the owning bead; it is never bound to something else.

Make a skin, step by step

Five small exercises, from one colour to a whole App. They follow the Design Book's customisation scenes U01 to U05. Writing and validating work today; trying a skin on in the running application is the next piece to land.

  1. Change a colour Built

    Start from the smallest valid skin and override one open token. Secondary text on panels, lighter:

    { "schema": "dna.skin/1", "id": "mine", "name": "Mine",
  "theme": { "base": "cockpit-dark", "density": "working",
             "overrides": { "ink.secondary": "#A4B8C2", "ink-3": "#A4B8C2", "surface.panel": "#22343C" } } }

    Pick a colour that is too dim and the skin is refused. With "ink.secondary": "#7D97A0" on that panel the CLI exits with code 2 and names the pair: ink-2 on paper-2 has …:1 contrast, minimum 4.5:1.

  2. Rebind a key Built

    Give Classic's "Edit the cell" a second chord while the grid is in Ready mode:

    "keymap": { "profile": "excel-365-win-en-us", "bindings": [
  { "when": "view:classic && mode:ready", "chord": "Ctrl+Shift+E", "command": "grid.edit-cell" } ] }

    Try "chord": "Escape" and the answer is Escape is reserved. Bind the same chord twice under conditions that can both hold and it is Overlapping skin bindings for Ctrl+Shift+E. Command ids are the ones the command search (Alt+Q) lists: grid.edit-cell, grid.move-down, grid.clear-contents, edit.undo, calc.calculate, view.notebook, inspector.details and the rest.

  3. Add a panel page In build

    Write a dna.page/1 tree under pages and name its id in shell.panels.right, as the audit-rail page in section 6 does. The page validates today; docking a skin's page in the running shell waits for manifest loading.

  4. Restyle Classic In build

    Combine the pieces: a dark base, larger formula text, a compact Deck and a trace instrument docked at 320 px. That is the complete example in section 6. Note what it leaves alone: row heights and cell formats are workbook content, and changing them would be a model change, not a skin.

  5. A three-line App Built

    An App is a page stored in the workbook, not in a skin. Three inputs and a result:

    { "schema": "dna.page/1", "title": "Loan", "root": { "kind": "stack", "children": [
  { "kind": "part", "id": "rate",  "component": "input", "bind": { "value": { "anchor": "…a2", "address": "Loan!B2" } } },
  { "kind": "part", "id": "years", "component": "input", "bind": { "value": { "anchor": "…a3", "address": "Loan!B3" } } },
  { "kind": "part", "id": "pay",   "component": "value", "bind": { "value": { "anchor": "…a4", "address": "Loan!B4" } } } ] } }

    In the application you do not type anchors. The Forms maker lists candidate inputs from the workbook (InputCandidates: unlocked or validated cells), and "Add selected cell to page" creates the anchor and patches the page in one batch. The App view then runs the page with no authoring handles.

Try it on, and keep it Designed

The design is one banner: Trying "Calm Review" · Keep for this file · Keep for me · Discard. A skin under trial is mounted and can be discarded with Esc. Keeping it for the file writes one presentation change; the model revision does not move. When a workbook you receive carries a skin, its pages and per-view settings apply on open, and its theme, key bindings and shell layout are only offered under the same banner. A file never rebinds your keyboard unasked.

08

What skins can and cannot do

The limits are the feature. They are what makes it safe to open a stranger's workbook and to let an agent restyle yours.

A skin can

  • Choose a theme and a density, and move the neutral tokenswithin the contrast law
  • Set the size of formula text10 to 32 px
  • Add or change key bindings over the view's profileand see how many keys depart from Excel
  • Name a sequence of built-in commandsrun on request, through the normal undo
  • Dock instruments and its own pages beside any view
  • Pin extra read-outs to the Strip
  • Carry pages of bound componentsinputs, values, row windows
  • Pass settings to a viewthe view decides what they mean
  • Travel inside a workbook, or stay with you

A skin cannot

  • Change how anything calculatesno engine handle crosses the contract
  • Contain code, expressions, HTML or URLsthe schema has no field for them
  • Edit a cell, a formula, a name or a format by being appliedapplying a skin is a presentation change; Stamp.model does not move
  • Recolour red, amber, signal orange or green
  • Break a sanctioned contrast pair
  • Rebind Esc, Ctrl+Z, Ctrl+Y, F4, Ctrl+Enter, Alt+Q, or the way back to Classic
  • Hide the Strip or a trust prompt
  • Run anything when a workbook opens
  • Add a new kind of component or a new viewthat is an extension, or a crate

When data is not enough: the extension boundary Designed

A new kind of visual component needs code, and code never comes from a file. The design is an installed, signed package (.dnaext: a manifest and a Rust-compiled Wasm module) approved once through a trust card. A workbook or skin names the extension by id and version in requires; it never carries it.

Why files never carry code. A spreadsheet is the document people forward without thinking. If presentation could carry behaviour, every received workbook would be a program to audit. Keeping skins and pages as data means the question "what will opening this do?" has one answer: draw.

Proposal and Decide

The default policy for an agent is Propose: it may not commit. It sends a proposal made of units, each a batch with the units it needs. The person ticks a subset and sees the writes for exactly that subset. Decide checks every accepted unit against its base and expects together and refuses all of them if any is stale. Each accepted unit becomes its own Origin::Agent history entry in one group, so Ctrl+Z takes back one unit at a time. An agent connection cannot change macro security, load an add-in, install an extension, or save over a file.

A worked example

The brief: "Turn Loan.xlsx into a planner: inputs for loan, rate and years; show the payment and the schedule."

  1. Look, do not invent

    Ask InputCandidates { scope } for the cells the workbook itself marks as inputs, and Structure { scope } for its tables and formula runs. The payment formula already exists in Loan!B4. A page holds no formulas, so there is nothing to duplicate.

  2. Write the page

    Produce loan-planner.dnapage.json (in docs/guide/skinning/examples/): three input parts, one value, one data-frame, each with a Bound { anchor, address }.

  3. Validate against the workbook

    dnacalc skin validate loan-planner.dnapage.json --workbook Loan.xlsx --json. Each anchor must already be in the workbook's view part (a PresentationChange::Bind puts it there) and must resolve to the same source as its address. One that does not comes back as <address>: Source missing. Fix the page; do not move the binding to a nearby cell.

  4. Hand it over

    Offer the page as a presentation change. If you also want a defined name added, that is a separate model proposal, previewed on its own.

  5. Check what the person sees

    On the page, __dnaProbe() returns the selection, the visible cells with provenance, the draft and the stamp. This is real output from the published preview:

    { "active": [0,0,4,2],
  "cells": [ { "at": [0,0,1,1], "input": "Loan", "text": "Loan",
               "shown": { "provenance": "Literal", "value": { "Text": [76,111,97,110] } }, "spill": null, "style": 0 }, … ],

If you are adding a view rather than a skin, the test to copy is apps/dna-shell/tests/session.rs: it joins a view's commands, the keymap and the Session to the real calc-skin-host by packets, with no browser. Test commands and watches that way before drawing a pixel.

Guarded execution and skins

Macros and add-ins are code; skins and pages are not. The two meet in a few well-marked places.

DNA Calc runs code at one of three levels: Off, Guarded and Unguarded. Guarded is possible because DNA Calc owns the interpreters for VBA and embedded JavaScript, so it constructs their authority: a Guarded macro has no ambient reach, and every outside effect is a call on something the host handed over. Native add-ins (XLL, COM) cannot be mediated in process, so under Guarded they are not loaded. The full design is in docs/design/GUARDED_EXECUTION.md.

Where they meetHowState
One selectionA macro's Range.Select moves the same selection every view shows. The host reports the move with its cause, SelectionCause::Macro { procedure }, so a late echo of the person's own cursor cannot undo it.Built
One historyOrigin::Macro { run, procedure } entries sit in the same history as view edits. Grouping a whole run into one entry is the first-release design.In build
Screen updatingWhile ScreenUpdating = False, the host sends no frames; views repaint when it returns.Built
CapabilitiesA view learns what the host can run from Capabilities.supported (Vba, NativeAddins, ComRtd) and never branches on the platform.Built
Running a macro from a pageAn action button names a macro; it runs under the workbook's level, with the first outside reach asked as a typed question rather than a blanket "enable macros".Designed
A macro asking for a viewApplication.Run "DnaCalc.View.Switch", "notebook": late-bound, so the same workbook still compiles and runs in Excel. Applied when the run yields; it creates no undo step.Designed
Previewing a macroA Guarded run without grants has no outside effects, so it can run on a fork and show its writes in the same Preview.writes terms as an agent's proposal. Apply adopts the fork; it does not run the macro again.Designed

Two grants that never imply each other: trusting an add-in to calculate does not let it draw, and trusting an extension to draw does not let it register a function or reach the engine.

Scale, platforms, testing, accessibility

Budgets and big workbooks

Every query takes a Budget { cells, nodes, edges, bytes, millis }. A view never mounts blind: the shell asks for a Census (counts taken without calculating) and calls View::fit. A view that cannot show a workbook honestly says so before it draws, with at least a reason and commands that lead somewhere useful.

Whole

The view shows the workbook as it is. Classic always answers this.

Simplified

"Showing shown of total", with the explanation. The Stage carries the note.

Declined

The view does not mount. The shell shows the reason and the ways forward, each a command.

The grid watches one 36 by 18 page of cells at a time, as binary tiles. The Inspector's instruments ask with a budget of 800,000 cells and 8 seconds and report Coverage::Partial when they stop early. Calculation runs in slices (SkinHost::advance), so a long recalculation does not block typing. Latency targets (first viewport under 1 s, key echo under 50 ms, view switch under 150 ms) are design targets to be measured as benchmarks, not claims.

Accessibility

The contrast law is enforced where skins are loaded, so a skin cannot produce unreadable text. Colour is never the only cue: provenance is a word as well as a tint ("Saved value", "Previous calculation"), and the state badges in this guide follow the same rule, solid for built and dashed for designed. Pages are flow layouts with real form controls, labels, table captions and role="alert" on errors, so they reflow at high zoom. The Strip is a role="status" region. The key that leaves any state, Esc, and the way back to Classic cannot be taken away by a skin.
