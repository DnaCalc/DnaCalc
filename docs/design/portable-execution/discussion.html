Portability, beside Guarded

Guarded asks "may this code do it?" Portability asks "can this host do it?" Both are questions about capabilities, so they share one vocabulary and one declaration per member of every API face: VBA, the Excel object model, COM classes, Win32 Declares, the C API and worksheet functions.

Design pass by Fable (docs/design/PORTABLE_EXECUTION.md, 1,042 lines, nine data files, bead dc-54aki), measured on the Linux corpus run. Synthesis and recommendations by the coordinator.

  • 45% of macro entries that ran on Linux succeeded
  • 83% of clean projects need nothing a Linux desktop lacks
  • 6 decisions for you, at the end
Fable · the model

Two questions, one vocabulary

A capability is something the host can hand to code: a file tree, the network, a dialog, a COM class. Each API member declares what it needs. Each host profile says how it provides each need. The verdict for a member on a host is computed from the two, never written by hand per cell.

One verdict vocabulary

CalcVBA's six words plus one for the meeting point with Guarded. Ordered by how much of Excel-on-Windows they give:

reject < mediated < replace < shim < host < model < native

VerdictMeaningExample
nativethe host has it as Excel has itRange.Value, charts, every worksheet function
modelwe model it inside the enginethe internal clipboard, Application.Run, XLM
hostthe host app provides its own form of itMsgBox, printing, the clock
shimtranslated at the boundary, same behaviourpaths through the mount table, Environ
replacea portable implementation of the same classScripting.FileSystemObject in Rust
mediatedavailable only through a person's act or a granta file picker in the browser, ShellExecute "open"
rejectnot on this host; Excel's own error plus a typed NotAvailableHereFindWindowA, Outlook, a PE XLL on Linux
The key insight in Fable's pass: a host is just a machine on which some things aren't installed, and Excel already defines what happens then. An unregistered class raises 429, a missing DLL raises 53 at the first call, a missing drive raises 68 or 76. A portability refusal reaches VBA as that same Excel error and reaches the host as a typed NotAvailableHere. So refusing lazily, at the call, is not new behaviour. It is Excel's.

Fable · hosts

Hosts form a lattice, and the web is two hosts

You were right that web and wasm differ. "Web-hosted" means our server runs the engine: a per-user session store, server-side network under policy, no access to your disk. "Web-wasm" means the engine runs in your browser: OPFS storage, the file picker, fetch under CORS, and synchronous VBA I/O only inside a Worker that can block.

A profile maps each need onto the verdict chain, so profiles are ordered pointwise and form a lattice: a product of chains, not a ladder. server has files and no UI; web-wasm has UI and no free files, and neither is above the other. So a workbook carries a footprint (a set of needs) and gets a verdict per host, not a single "portability level". The meet of all profiles is the portable core. And Guarded with no grants is just one more, very low, profile, so "can it run on WASI?" and "can it run Guarded with a folder grant?" are answered by the same check.

Fable · paths

Paths are resolved, never rewritten

c:\Temp\MyFile stays that string inside the macro. The file facet resolves it through a per-session mount table, as Plan 9 namespaces and Wine's drive map do. The macro sees a Windows persona, because it was written against Win32.

# ~/.config/dnacalc/mounts.toml  (a workbook session may add or remove)
[[mount]]  windows = 'C:\'                         host = '~/.local/share/dnacalc/drive_c'  # private, never /
[[mount]]  windows = 'C:\Users\{user}'             host = '~'
[[mount]]  windows = 'C:\Users\{user}\Documents'   host = '{xdg:DOCUMENTS}'
[[mount]]  windows = 'C:\Temp'                     host = '~/tmp'                            # your example
[[mount]]  windows = '\\fileserver\finance'        host = '/mnt/finance'  mode = 'read'

Rules

Longest prefix wins, compared case-insensitively. C: is a private directory, never the host root. The workbook's own folder is always mounted while it is open, which makes ThisWorkbook.Path & "\data.csv" work. Unmapped means absent: ChDrive "Q" raises 68, as on a PC without a Q: drive.

Win32 quirks kept

Case-insensitive lookup with case-preserving creation (two names differing only in case is an error). Dir returns names sorted as NTFS does, not in ext4 hash order. Trailing dots dropped, CRLF and the project code page on write, archive bit on new files, so GetAttr returns 32.

The same table is the Guarded grant

Under Guarded, the grant is the mount list. No file grant means an empty table; "this workbook's folder, read only" means exactly one read mount. One mechanism serves both axes. A file the person picks creates a session mount: the pick is the grant.

Environ("TEMP"), USERPROFILE and APPDATA return persona paths backed by mounts. USERNAME and COMPUTERNAME return the real host names. OS returns Windows_NT. Host variables pass through only by name. Device paths, pipes, alternate streams and raw volumes are refused everywhere.

Fable · COM

COM without COM, and no DCOM

VBA needs the Automation object protocol: invoke by DISPID, type information, enumerators, events, identity. It does not need activation, apartments, marshalling, monikers or a registry. Two tables replace those.

References resolve by typelib GUID to one of three states. Implemented: compiles and runs on our class. Types only: compiles against descriptors extracted on Windows, and New raises 429. Unknown: the reference is missing. In each case only the procedures that use the library fail; the rest of the project runs, which is kinder than VBA's compile-time "Can't find project or library". On Windows, real COM stays available as a host capability.

XLLs: three options

A · refuse foreign binaries

A PE XLL off Windows is NotAvailableHere { NativeAddins }. Today's rule; keep it as the default for existing binaries.

B · source-compatible XLL

The same exports and Excel12 callback built as ELF or Mach-O. calc-xll-abi already compiles and passes its layout tests on Linux.

C · XLL compiled to wasm

The same C source for wasm32, whose only imports are the C API callbacks. A wasm module has no ambient authority, so it is contained by construction, and it runs on every host, the browser included. Fable prefers C.

Most of the C API is portable because it works on the model. Host reach sits in xlfRegister/xlfCall/CALL (FFI), the path and identity info types of xlfGetWorkspace and xlfGetDocument (persona), the XLM file functions (same file facet as VBA), xlfExec/SendKeys and DDE (reject).

Workbooks without macros have footprints too

Formulas are code, so a workbook's footprint is the join of its VBA and its formulas. CELL("filename") and INFO("directory") need the persona (today: typed refusals). WEBSERVICE and IMAGE need the network, and in the browser mediation. RTD off Windows is #N/A, which is Excel's own value for a server it can't create. Microsoft-service functions (STOCKHISTORY, COPILOT, PY) are rejected on every host, Windows included.

Fable · theory

The computer science underneath

An effect system

A procedure's footprint is its effects, closed over the call graph: may effects (some path reaches it) versus must effects (every path does). Effects pass up through calls, like effect polymorphism.

Constant propagation

Most late binding is literal: CreateObject("Scripting.FileSystemObject"), path prefixes, Application.Run names. Propagating those strings turns late binding into a static answer.

Sound by construction

The static scan over-approximates. The run-time NotAvailableHere, delivered as Excel's own error, is the safety net that keeps the whole thing sound when the analysis guesses wrong.

Object capabilities

Both axes are the object-capability model: code reaches only what it was handed. Guarded decides what is handed over; the host profile decides what exists to be handed.

Namespaces

The mount table is a per-session namespace, as in Plan 9. Wine's dosdevices is the precedent on the same Windows-path problem.

A lattice of profiles

Profiles ordered pointwise over the verdict chain form a product lattice. A footprint that runs on a profile runs on every profile above it, so testing one host also answers for the richer ones.

Coordinator · synthesis

What I take from it

  1. Portability is not today's bottleneck on Linux; object-model coverage is. Of the 1,345 run entries that did not succeed, 1,241 stopped at product gaps: members not modelled yet (Window.SelectedSheets 87, SmallScroll 60, Range.Sort custom order 36) and VBA errors. Only about 150 stopped for a portability or grant reason. A further 322 projects never got admitted (compile refusals 130, locked projects 75). So for "runs on Linux", the biggest lever is still the macro-host work already under way (dc-oxh8w, dc-cmruz). Portability work pays mostly on the suspect corpus and on the web.
  2. Within portability, the order is clear from the data. The two cheap decisions first (reject per call, lazy references), because they let whole projects run around one bad procedure. Then the path persona and mount table (P1). Then UserForms, which appear in 104 clean projects and are the largest "replace" item. Then FileSystemObject, ADODB.Stream and the HTTP classes. The Declare table last, because almost all of it serves triage-suspect projects.
  3. The persona is a choice, and it should be visible. Windows-faithful by default is right: it bit-matches Excel and keeps old macros working. But INFO("osversion") answering Windows (64-bit) NT 10.00 on Linux is a white lie. I'd keep CalcVBA's existing native mode as an opt-in for new code, and show the persona in the Strip ("Windows persona · Linux host") so nobody is surprised.
  4. Web-wasm needs a hosting decision. Synchronous VBA file and network calls in the browser need a Worker that can block, which means serving the app with COOP/COEP headers (or JSPI when it ships). Those headers affect embedding and third-party resources on dnacalc.com, so it's a deployment decision, not only an engine one.
  5. Measure the friendly profile next. The measurement is the strictest Linux case: headless CLI, Guarded, no grants. The Linux desktop under Unguarded, where MsgBox answers and files open through the mount table, isn't measured yet. That's the number to put on the website, and it needs the path persona first.
  6. The badge is the product. A per-host badge on each workbook (from dnacalc portability <book> --host <h>), with a per-entry list behind it, turns this whole matrix into one line a user can read: runs anywhere · desktop · Windows · needs Excel.
For discussion

Six decisions

  1. Reject per call in faithful mode, so CalcVBA's "reject at load" applies only in strict mode. Recommended: yes. This is what lets the chart button run in a project that also has a FindWindow call.
  2. Unknown references: modules that don't use the library still run. Recommended: yes.
  3. XLLs: source-compatible (B) and/or compiled to wasm (C). Recommended: decide once the Linux C API dispatcher exists; prefer C.
  4. Four new shared capability names: ui.dialog, ui.filedialog, clipboard, print, allowed under Guarded as today so the audit shows them. Recommended: add now.
  5. Default mounts: map C:\Users\{user} to your home directory, or use a private tree with only the workbook's folder mounted. Recommended: private tree plus the workbook's folder under Guarded; home mapping under Unguarded.
  6. Shell: no general shim. Recommended: keep reject plus CalcVBA's per-project command map; never translate command lines.

Decided 2026-11-28: all six as recommended, with three refinements. (2) The report and badge list every unknown reference even when nothing uses it yet, so a workbook with a dormant reference is never shown as plainly portable. (3) XLLs: source compatibility by plain C recompile against our #define headers, not a magic mechanism; no wasm XLLs for now. (5) The mount table is configurable host setup; the recommendation gives its defaults. (6) A careful Shell mechanism may come later. The beads are scheduled.
